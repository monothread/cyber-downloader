# Decisions

Format: `D-NNN` · date · status (accepted/superseded) · context · decision · consequences.

## D-001 · 2026-09-30 · accepted — Framework: Electron + React + TypeScript
- **Context:** Linux desktop app in TypeScript with a cyberpunk theme (rich CSS).
- **Decision:** Electron + Vite (`electron-vite`) + React. Rejected alternatives: Tauri (part of it in Rust), Electron without React.
- **Consequences:** larger binary (~100MB+); simple UI and styling; everything in TypeScript.

## D-002 · 2026-09-30 · superseded by D-013 — System yt-dlp/ffmpeg
- **Decision:** detect `yt-dlp`/`ffmpeg` on the PATH (configurable path) + an update button for yt-dlp. Do not bundle binaries.
- **Consequences:** required a prior installation; the UI had to warn when a binary was missing.

## D-003 · 2026-09-30 · accepted — Initial scope
Includes: queue with progress (speed/ETA/cancel), audio-only mode (mp3/m4a/opus), playlists and subtitles, persisted history, browser cookies, default folder, best audio+video, output format, title length limit, friendly errors.

## D-004 · 2026-09-30 · accepted — Supporting stack
Zustand (state), Vitest + Testing Library (unit), Playwright-Electron (e2e), ESLint `--max-warnings=0`, `electron-builder` (AppImage + deb). Persistence: see D-008 (originally `electron-store`).

## D-005 · 2026-09-30 · accepted — Long titles
Setting `maxTitleLength` (default 80) → `-o "%(title).{N}s [%(id)s].%(ext)s"` + `--trim-filenames`; optional `--restrict-filenames`. Avoids failures caused by the 255-byte filesystem limit.

## D-013 · 2026-09-30 · accepted — Binaries bundled in the app (supersedes D-002)
- **Decision:** the package ships yt-dlp (`yt-dlp_linux`), ffmpeg + ffprobe (static build) and deno in `resources/bin` (copied to `<resources>/bin` through `extraResources`). Downloaded by `scripts/fetch-binaries.mjs` (`npm run fetch-binaries`, run by `npm run dist`), each one verified by checksum (sha256/md5).
- **Resolution (`BinaryResolver`):** yt-dlp = custom path → `userData/bin/yt-dlp` (updated) → bundled → system. ffmpeg = custom → bundled → system. `--ffmpeg-location` receives the bundled folder (ffmpeg+ffprobe) or the custom path.
- **JS runtime:** the yt-dlp process gets a `PATH` with the bundled folder first, so the bundled deno is found without `--js-runtimes`; the `jsRuntime` field becomes an optional override.
- **Updating:** without a custom path, downloads `yt-dlp_linux` from the latest GitHub release (compares `tag_name` with `--version`, verifies `SHA2-256SUMS`) into `userData/bin/yt-dlp`; with a custom path, runs `-U` on it. The AppImage is read-only, which is why the updated binary lives in userData.
- **Licenses:** `resources/THIRD_PARTY_NOTICES.md` ships with the package (ffmpeg is GPLv3; text in `bin/ffmpeg-GPLv3.txt`).
- **Consequences:** AppImage ~256 MB, deb ~210 MB; the deb no longer depends on the apt yt-dlp/ffmpeg.

## D-014 · 2026-09-30 · accepted — App self-update via electron-updater + GitHub Releases
- **Decision:** `electron-updater` with the `github` provider (`monothread/pullwave`, public repo), `autoDownload=false` and `autoInstallOnAppQuit=false`: the user clicks to download and then to restart/install (avoids killing downloads without warning).
- **Code:** `AppUpdateService` (state machine idle/checking/available/downloading/downloaded/not-available/error/unsupported, with an injectable `UpdaterLike`) + `electronUpdater.ts` (adapter); IPC `app-update:*` and event `event:app-update-state`; UI: `UpdateBanner`, `UpdateActions` and an "APP UPDATES" section in Settings; setting `checkUpdatesOnStart` (on by default, checks 5 s after opening, packaged app only).
- **Packaging:** `artifactName: pullwave-${version}.${ext}` (no spaces, so it matches `latest-linux.yml`); `npm run dist` uses `--publish never`, `npm run release` publishes (as a draft) using `GH_TOKEN`.
- **Rejected alternatives:** a custom updater (reimplements integrity/differential download) and a notification-only link (does not update with one click).

## D-015 · 2026-09-30 · accepted — Settings auto-save and one-input-per-link URL entry
- **Settings:** the "SAVE SETTINGS" button was removed. Toggles and selects save immediately; text and number fields save 2 s after the user stops typing (`useAutoSaveSettings`, `AUTOSAVE_DELAY_MS = 2000`). Pending edits are flushed when the panel unmounts (tab switch). A status line shows: saved automatically / unsaved changes / saving / all changes saved / error. The sanitized value returned by the main process replaces the draft only if the user did not type again meanwhile.
- **Store:** `saveSettings` re-checks the binaries only when `ytdlpPath` or `ffmpegPath` changed (auto-save would otherwise spawn yt-dlp/ffmpeg on every save).
- **Downloads:** the multi-line textarea (URLs separated by spaces/new lines) was replaced by one single-line input per link plus a "+ ADD LINK" button and a remove button per row. The input is not resizable; long links scroll inside the field (ellipsis when unfocused, full value in the tooltip) and never overflow the page. On DOWNLOAD the accepted links leave the list, rejected ones stay with an inline error, and an empty list resets to a single empty row. `addUrls(urls: string[])` now returns the per-link results and `splitUrls` was removed.

## D-016 · 2026-09-30 · accepted — Quit cleanup, update-state guard and smaller IPC surface
- **Quit:** `QueueManager.shutdown()` (called on `before-quit`) cancels every running process and stops the queue from starting new ones. Before this, a silent child (e.g. an ffmpeg merge) could keep running after the window closed. Covered by an e2e test using a fake yt-dlp that stays silent (`quiet` URLs); without the fix that test fails.
- **App update:** `AppUpdateService.check()` is ignored while an update is already downloaded, so the "ready to install" state is not reset to "available".
- **IPC:** the unused `shell:open-path` channel (`openPath`) was removed: `shell.openPath` can launch any file with its default program and nothing in the UI needed it. `shell:show-item` (reveal in folder) stays.

## D-017 · 2026-09-30 · accepted — Close to system tray
- **Setting:** `closeToTray` (off by default; Settings > WINDOW). When on and a tray is available, closing the window hides it (downloads keep running); the tray icon has a menu with "Show Pullwave" and "Quit", and a click on the icon toggles the window. "Quit" and closing the window without a tray ask for confirmation when downloads are running or queued ("N downloads are still in progress"); other quit paths (auto-update restart, logout) still cancel silently through `before-quit`.
- **Universal approach:** Electron's `Tray` uses the StatusNotifierItem (SNI/AppIndicator) D-Bus protocol, implemented by KDE Plasma, Cinnamon, XFCE, MATE, LXQt and by GNOME through the "AppIndicator and KStatusNotifierItem Support" extension. Verified on Cinnamon: the item registers on the `org.kde.StatusNotifierWatcher`, its menu is `Show Pullwave / Quit`, and it disappears when the app quits.
- **Availability check (`trayAvailability.ts`):** asks the session bus (`gdbus`) whether `org.kde.StatusNotifierWatcher` has an owner. If yes → available. If not and the desktop is GNOME (`XDG_CURRENT_DESKTOP` contains `GNOME`) → unavailable, because stock GNOME has no tray and hiding the window would make the app unreachable; then closing the window quits normally and Settings shows a warning about the extension. Any other desktop is assumed to have a tray even when the check is inconclusive.
- **Safety net:** the app is single-instance (`requestSingleInstanceLock`); launching it again shows the hidden window.
- **Code:** `TrayManager` (creates/destroys the tray when the setting changes, injectable), `windowClose.ts` (`decideCloseAction`, `requestQuit`, `createQuitRequester` that avoids stacked dialogs), `electronTray.ts` (thin Electron adapter), `QueueManager.pendingCount()`, IPC `tray:support` and `onSettingsSaved`.

What was verified: the fetch script for both platforms, an unpacked Windows layout, the platform-dependent code through unit tests, and the Linux packages.

## D-019 · 2026-09-30 · accepted — Stream finder for pages yt-dlp does not understand
- **Flow:** when a download fails with `UNKNOWN` or `OUTDATED` (covers "Unsupported URL" / "Unable to extract"), the job card offers **FIND STREAM**. The search runs in stages and nothing is downloaded without the user's choice: 1) the normal yt-dlp attempt already failed; 2) **static scan** of the page HTML; 3) only if that finds nothing (or the user presses "NOT THE ONE? SEARCH DEEPER"), a **hidden browser window** that watches the page's network. The user then picks one of the candidates, which becomes a normal download job.
- **Static scan (`pageScanner.ts`):** fetches the page (browser-like headers, 15 s, 5 MB cap) and looks for media addresses (`.m3u8/.mpd/.mp4/.webm/.m4v/.mov`) in `<video>/<source>`, scripts, JSON (escaped slashes decoded), `og:video`/`twitter:player:stream` and `<base href>`; it follows iframes up to 2 levels and at most 6 pages. Page candidates carry the page that contained them as the referer.
- **Hidden browser (`browserSniffer.ts`, rules in `sniffRules.ts`):** sandboxed `BrowserWindow` with `show: false`, no Node, throwaway in-memory session, all permission requests denied, downloads blocked, popups denied, no navigation away after the page loaded, audio muted. Images/fonts/pings are cancelled; HLS/DASH playlists are let through, plain video files are recorded and cancelled (only their address matters) and stream pieces (`.ts`, `.m4s`, keys, subtitles) are ignored. Media served from extension-less addresses is recognised by its `Content-Type` (files under 100 KB are ignored). It tries to start playback (muted `video.play()`, common play buttons, a click in the middle) and stops after 25 s, or 4 s after the first stream (`PULLWAVE_SNIFF_TIMEOUT_MS` overrides the timeout for tests/debugging).
- **Candidates (`streamFinder.ts`):** ordered HLS, DASH, MP4, WEBM, other. The screen only receives the address, type, host, origin (page/network) and page title; the referer, user agent and the cookies the throwaway session received for that address stay in the main process and are applied to the download (`--referer`, `--user-agent`, `--add-header Cookie:…`). The file is named after the page title (escaped for yt-dlp's output template). `playlistFilter.ts` drops the quality variants that a master HLS playlist in the same list already covers.
- **Safety:** addresses on the user's private network (localhost, 10/8, 172.16/12, 192.168/16, link-local, `.local`, IPv6 ULA) found *inside* a public page are never followed or offered, unless the page itself is private; only http(s) is accepted; a search can be cancelled; old candidates are forgotten when a job searches again.
- **Limits, stated in the UI:** DRM-protected streams (Widevine etc.) are not bypassed and will fail in yt-dlp; sites that need a login or an interaction the app cannot do may show nothing. The feature is for content the user has the right to download.
- **Tested with:** local pages in the e2e suite (static `<video>`, iframe, a player built by JavaScript, an empty page, cancelling) and, by hand, a public hls.js demo page playing a Mux test stream (yt-dlp failed on the page; the finder found the master playlist via the network; the download started with the right referer).

## D-021 · 2026-09-30 · accepted — Hidden browser: visible page, scrolling to the player, play in every frame
- **Problem:** embedded players are usually an iframe of another origin, below the fold, that only arm themselves when the page is *visible*, need a user gesture to start and then request the video through a signed address without extension. A plain hidden window found nothing there.
- **Changes in `browserSniffer.ts`:** the window is rendered **off-screen** (`offscreen: true`, frames consumed at 15 fps) so `document.visibilityState` is `visible`; each play attempt first **scrolls the biggest player-like element into view** (lazy players wait for that), then runs a play script **inside every frame of the page, including cross-origin iframes** (`webFrameMain.executeJavaScript(..., userGesture = true)`): videos are played muted and the element in the middle of the frame gets pointer/mouse events and a click. Attempts repeat at 1.5, 4, 8 and 13 s so lazily created frames are reached.
- **What did not work and was dropped:** routing a real mouse click (`sendInputEvent`, and the DevTools `Input.dispatchMouseEvent`) into the cross-origin iframe of an off-screen page did not reach it in the tests.
- **Tested with:** local pages only (an e2e that reproduces the mechanism: lazy cross-origin iframe, visibility check, user-gesture check, signed extension-less `video/mp4` address). The test fails with the previous sniffer and passes with this one. It was deliberately not tried against any real streaming site, so nothing is promised about how a given site behaves.

## D-022 · 2026-09-30 · accepted — HTTP 403 message and grouping of near-identical streams
- **Why:** a stream found on a page can be a temporary, signed address. The same video is often requested several times through slightly different addresses (another mirror host, redirects that append session parameters), so the list showed "a lot of streams" that were one video, and a refused download showed yt-dlp's raw error with a very long URL.
- **Error:** new code `FORBIDDEN` (HTTP 401/403/410 or "Forbidden"), matched **before** `NETWORK` because yt-dlp reports it as "Unable to download webpage: HTTP Error 403". Title "Access refused by the server"; the hint explains that the link may have expired or be tied to the original session, network or browser. The raw text stays available under "SHOW DETAILS". `FORBIDDEN` does not offer FIND STREAM.
- **Grouping (`streamGrouping.ts`):** after the `playlistFilter` step, candidates of the same kind and path are folded into one when they share at least 4 query parameters with the same value and those make up at least 60% of the shorter address's parameters, **unless** a parameter that identifies the content or quality (`id`, `sig`, `signature`, `token`, `hash`, `key`, `v`, `vid`, `video`, `video_id`, `videoid`, `file`, `fid`, `itag`, `format`, `quality`) has different values. The first address seen (the one the page asked for) represents the group and the list shows "+N alternate address(es)". Plain overlap alone was not enough: two different videos from one host share most routine parameters, which the tests caught. Mirrors without query parameters are never merged.
- **Not done on purpose:** nothing was changed to make any particular site's download succeed; the test data is anonymised and modelled on the pattern, not taken from a real site or user.

## D-023 · 2026-09-30 · accepted — Temporary addresses: same IP family and a fresh link after a 403
- **Why:** many stream addresses are temporary and signed, and only accept a request that looks like the page's own. Two of the usual reasons a download is refused with HTTP 403 are an address bound to the IP that asked for it (with IPv4 and IPv6 available, the page and yt-dlp may leave through different families) and an address that expired or belongs to another session.
- **IP family (`boundIpFamily` in `mediaKinds.ts`):** when a candidate's address carries the requester's IP in `ip`, `clientip`, `client_ip` or `cip`, the download gets `--force-ipv4` or `--force-ipv6` accordingly (`RequestExtras.ipFamily`). Addresses without such a parameter are left alone. The family is kept with the candidate in the main process and is also re-applied when the job is retried.
- **Fresh link:** jobs created from a stream remember the page they came from (`DownloadJob.pageUrl`). If one fails with `FORBIDDEN`, its card offers **FIND A FRESH LINK**, which runs the stream search again on that page (`stream:find` uses `job.pageUrl ?? job.url`), so the user picks a new address with a new signature. The page address is never passed to yt-dlp.
- **Generic on purpose:** nothing here knows about any site; it reacts to what the address and the job contain. The e2e suite proves each behaviour with a local server (IPv4-bound, IPv6-bound, unbound, refused stream) and the unit tests cover the parsing and the arguments.
- **Not done:** downloading through the same network session as the hidden browser (instead of yt-dlp) for addresses that stay refused; matching more headers (Origin, Accept-Language). If the refusal has another cause, these changes do not help.

## D-024 · 2026-09-30 · accepted — Linux ffmpeg: the shared BtbN build instead of the static one
- **Problem found while looking at live streams:** the static ffmpeg/ffprobe from johnvansickle.com (7.0.2) **crash with a segfault as soon as they read MPEG-TS**, the container of HLS segments. Verified directly: `ffmpeg -i seg.ts`, `ffprobe seg.ts` and `ffmpeg -i live.m3u8` die with a core dump (exit 139) on Ubuntu 24.04 (glibc 2.39), independent of CPU flags, while writing MPEG-TS and everything else works, and the system ffmpeg reads the same files fine. The likely cause is a fully static glibc binary trying to load host libraries at run time, which is a known way for static glibc programs to crash on another glibc. It breaks live recording and any HLS download that ends with a fix-up step in ffmpeg.
- **Decision:** on Linux `fetch-binaries` now downloads the **shared** GPL build from BtbN (`ffmpeg-n9.0-latest-linux64-gpl-shared-9.0`, checksum from the release's `checksums.sha256`). `ffmpeg`/`ffprobe` are tiny programs in `resources/bin` and their libraries (≈190 MB) are in `resources/lib`, found through the binaries' own RPATH `$ORIGIN/../lib`. Needs glibc ≥ 2.28 (every supported distribution). `electron-builder.yml` now declares `extraResources` per platform so that only Linux ships `lib/`. A marker file (`resources/bin/.ffmpeg-source`) makes the script replace an older, different ffmpeg by itself.
- **Verified:** reading `.ts`, recording a live HLS, MP3/Opus encoding and a complete HLS download through the app (playable mp4) all work with this build. Windows keeps the gyan.dev static build, which has no such problem.
- **Maintenance:** the build name contains the release branch (`n9.0`). If BtbN retires it, `fetch-binaries` fails with a clear message and the name in `scripts/fetch-binaries.mjs` has to be bumped.

## D-025 · 2026-09-30 · accepted — Live streams: measured progress, STOP & SAVE, wait and record from the start
- **Problem:** for a live stream there is no percentage, and when yt-dlp hands the recording to ffmpeg (HLS lives) it prints no progress at all while it runs, so the card looked frozen.
- **Detection:** yt-dlp prints `CYBERINFO|<is_live>|<filename>` right before each download (`--print before_dl:...`) and the progress template also carries `downloaded_bytes`, `elapsed` and `is_live`. The job gets `live: true`.
- **Progress is measured by the app:** while a live job runs, `QueueManager` ticks every `LIVE_TICK_MS`, computes the recording time from its own clock and the size from the `<file>.part` (or the final file). The card shows `RECORDING`, `● LIVE`, time, size and an indeterminate bar instead of a percentage.
- **STOP & SAVE:** sends SIGINT to yt-dlp, which finishes the file and keeps it (the job ends as COMPLETE). CANCEL is unchanged (SIGTERM, recording discarded). Quitting the app stops live recordings the same way (`QueueManager.shutdown`, waits up to 8 s, then cancels) instead of throwing the recording away.
- **Settings (LIVE STREAMS, both off by default):** *Wait for scheduled live streams* adds `--wait-for-video 30`; *Record live streams from the start* adds `--live-from-start` and `--downloader-args ffmpeg_i:-live_start_index 0`.
- **Limit of "from the start":** it only works when the source still offers the earlier part (YouTube/Twitch through `--live-from-start`, or an HLS playlist kept as DVR/EVENT). A sliding-window playlist that has already dropped old segments cannot be recovered; the recording then begins at the oldest segment still available. The setting's text says so.
- **Verified with:** a local HLS live simulator (event and sliding window) and the real yt-dlp + ffmpeg (SIGINT keeps a playable file, from-start gets the earlier segments of an event playlist), unit tests and e2e with the fake yt-dlp. Nothing was tested against any real site.

## D-026 · 2026-09-30 · accepted — Themes: device (default), cyberpunk, dark and light
- **What:** a `theme` setting (`device` | `cyberpunk` | `dark` | `light`, sanitized, default `device`) chosen in Settings > APPEARANCE & WINDOW. It is saved with the other settings and read again when the app opens. `device` follows the system light/dark mode (`prefers-color-scheme`) and changes live when the system does. `App` sets `data-theme` on `<html>` to the resolved theme (`resolveTheme.ts`); the last choice is also kept in `localStorage` so the first paint already uses it.
- **How:** every colour, glow, scanline and corner cut in `cyberpunk.css` is a CSS variable; `themes.css` overrides them for `dark` and `light` (plain system font, no glow, no scanlines, no glitch, rounded corners). Adding another theme is a new block of variables.
- **Known limit:** on the very first run the page may show the system theme for a moment before the stored settings arrive from the main process.

## D-027 · 2026-09-30 · accepted — Windows: process tree kill, STOP & SAVE by salvage, diagnostics
- **Problem:** on Windows `child.kill('SIGINT')` does not send Ctrl+C, it terminates the process, and killing yt-dlp alone leaves the ffmpeg it started running. Verified on Linux by killing yt-dlp with SIGKILL during a recording: the ffmpeg kept writing and held the pipe open.
- **Cancel:** `killProcessTree` runs `taskkill /PID <pid> /T /F` on Windows (whole tree); SIGTERM elsewhere. yt-dlp is also spawned with `windowsHide` so no console window flashes.
- **STOP & SAVE on Windows:** there is no way to ask yt-dlp to finish, so the tree is killed and the run ends as `stopped`. The partial `<file>.part` of a live recording is MPEG-TS, which plays even when cut; `salvageRecording` copies it (`ffmpeg -c copy`, no re-encoding) into the final file and removes the partial. Checked on Linux: a SIGKILLed recording's `.part` is `mpegts`, and the remux gives a valid mp4. If that fails the job errors with a message and the `.part` is left. Quitting waits for the salvage. Linux keeps SIGINT.
- **Diagnostics:** `diagnostic.log` in the app data folder (256 KiB cap) records preload failures, page errors/warnings, a crashed or unloadable page and a missing `window.api` after load; a missing bridge shows an error box with the log path and the renderer shows a clear screen (`BridgeMissing`) instead of a dead UI. Added because buttons that depend on IPC reportedly did nothing on Windows and no cause could be found by reading the code; nothing here is a confirmed fix for that.
- **Not verified:** nothing Windows-specific could be executed on the Linux machine.

## D-029 · 2026-09-30 · accepted — Interface languages: English, Portuguese, Spanish, Chinese, Japanese
- **What:** a `language` setting (`device` | `en` | `pt` | `es` | `zh` | `ja`, sanitized, default `device`) in Settings > APPEARANCE & WINDOW. `device` uses the system language (`navigator.language` in the screen, `app.getLocale()` in the main process) and falls back to English when it is not supported. ## D-031 · 2026-09-30 · accepted — Live streams: double-check the end and show that it is waiting
- **End check (`verifyLiveEnd`, default on; `verifyLiveEndSeconds`, default 10, 1–120):** when a live recording ends (exit 0) or fails (e.g. dropped connection), the card is not finished at once. `QueueManager` keeps it `running` (so it holds its slot) with `endCheck { secondsLeft, totalSeconds }` and counts down every second. It asks yt-dlp again (first at once, then every `LIVE_END_RETRY_MS` after an attempt that found nothing): the attempt reuses the request but adds `--match-filter is_live` (so it is skipped when the stream is not live) and a part number to the file name (`… (part 2).ext`), and drops `--live-from-start` and `--wait-for-video`. If an attempt reports a live stream (`CYBERINFO|True`), the check closes and that attempt becomes the recording of the same card (time keeps counting; a new end opens a new check). If the time runs out, the card finishes exactly as the original run ended (done or error, history included).
- **What does not open a check:** STOP & SAVE (the user ended it on purpose, tracked in `stopRequested`), CANCEL, the Windows kill-and-salvage stop, quitting the app, and jobs that are not live. During a check, STOP/CANCEL mean FINISH NOW; removing the card or quitting drops the check and kills the attempt.
- **Several files:** a recording that resumes is written as one file per part. They are joined when the card ends (see D-034).
- **Waiting effect:** with *wait for scheduled live streams* on, yt-dlp is started with `--no-quiet` (otherwise `--print` silences its `[wait]` lines) and `runYtdlp` reports `[wait]` lines of stdout through `onWaiting`; the line splitter now also ends lines at a bare `\r` (yt-dlp rewrites its countdown with it). `waitingForLive` is cleared by the first recording or progress line. Without the setting nothing changes.
- **Visual:** `job--verifying` (amber pulse, badge blink, bar that drains over the checking time with a scan line, countdown text, FINISH NOW) and `job--waiting` (magenta pulse, radar sweep, animated dots); all colours and glows are theme variables and `prefers-reduced-motion` turns the animations off.
- **Verified with:** the real yt-dlp 2026.08.19 and a local extractor plugin: an upcoming live prints `[wait] Waiting for …` on stdout only with `--no-quiet`, uses `\r` for its counter, and `--match-filter is_live` skips a non-live video with exit 0 and no `CYBERINFO` while a live one goes on to download. Unit tests and e2e with the fake yt-dlp (`liveend`, `liveback`, `livewait`). Not verified against any real site; an extractor that does not fill `is_live` would make the attempts skip a stream that is live.

## D-033 · 2026-09-30 · accepted — CANCEL and STOP & SAVE no longer leave a recording stuck (Linux)
- **Problem (reproduced with the real yt-dlp and a local HLS live):** CANCEL sent SIGTERM to yt-dlp only. yt-dlp died, but the ffmpeg it had started (HLS lives) kept running and writing, holding the stdout/stderr pipes open. `runYtdlp` resolved only on the `close` event, which waits for those pipes, so the card stayed *RECORDING* for good (20 s+ in the test) and the `.part` kept growing. D-027 had already found this on Windows (`taskkill /T`); Linux was never covered.
- **Process group:** `defaultSpawn` starts yt-dlp with `detached: true` outside Windows, so it leads a group of its own, and `killProcessTree` signals the group (`process.kill(-pid)`), reaching ffmpeg too; a process that is not a group leader, or has no pid, is signalled alone.
- **Escalation:** CANCEL sends SIGTERM and, if the process is still there after `KILL_ESCALATION_MS` (3 s), SIGKILL. STOP & SAVE still sends Ctrl+C to yt-dlp alone (so it finishes and keeps the file); if it has not finished after `STOP_ESCALATION_MS` (10 s) the whole group is ended and the result is `stopped`, so the recording is salvaged exactly as on Windows.
- **Result without waiting for the pipes:** after the `exit` event the result is given at most `EXIT_GRACE_MS` (1.5 s) later even if the pipes are still open; whatever is left in the group is then terminated and the pipes are destroyed. The line splitter and Windows behaviour are unchanged.
- **Quitting:** `QueueManager.shutdown` also cancels a live recording that did not finish within its wait, so nothing keeps running after the app is gone.
- **Verified with:** the real yt-dlp 2026.08.19 and ffmpeg against a local HLS live (CANCEL ends in 2 s with no ffmpeg left; STOP & SAVE still ends in 3 s), unit tests with fake timers and a real process group, and e2e with a fake yt-dlp that leaves a process holding the pipes and ignores Ctrl+C. STOP & SAVE itself could not be made to fail with the real tools here; the escalation covers a yt-dlp that does not react to Ctrl+C. The effect of the detached group on Windows was not tested.

## D-034 · 2026-10-01 · accepted — Parts of a resumed live recording are joined into one file
- **Why:** when the end check (D-031) finds the stream again, yt-dlp records the next part in `… (part N).ext`; it cannot append to the finalized file of the previous part. Leaving one file per part forced the user to join them by hand.
- **How:** `QueueManager` joins the parts once, when the card ends (time ran out, FINISH NOW, STOP & SAVE or quit), never while recording. `mergeParts` (`partsMerger.ts`) runs ffmpeg's concat demuxer with `-c copy` (no re-encoding) on the parts in recording order (the paths in `outputPaths`) into `<first>.merging.<ext>`, replaces the first part with it and deletes the other parts. The card keeps `running` until it ends, and `shutdown` waits for it. While it runs `job.merging` is true: the card shows a JOINING PARTS badge (`job--merging`, green pulse, a bar with a scan line, no actions) in the five languages, and `livePhase` returns `merging` before `verifying` and `waiting`.
- **Only when:** the job is a live recording that resumed (`parts > 1`), more than one path was recorded, and the result is `done`. Playlists and non-live downloads are never joined; a card that ended with an error keeps its parts.
- **If it fails** (ffmpeg missing or error): every part is kept untouched and the card ends as before, with the last part as `filePath`.
- **Limits:** assumes the parts share container and codecs (true for the same stream); the time the stream was offline is simply skipped. Not verified against a real site, only with unit tests and e2e with a fake yt-dlp and a fake ffmpeg.
- **Saving state:** STOP & SAVE sets `job.saving` at once (before yt-dlp has closed the file, and through the salvage on Windows) and `finish` clears it. The card shows SAVING FILE (`job--saving`, cyan pulse, bar with a scan line, no actions) so the click has visible feedback and cannot be repeated. `livePhase` order: `merging`, `saving`, `verifying`, `waiting`. FINISH NOW needs no state of its own: without parts to join the card finishes at once, and with them it goes straight to JOINING PARTS.

## D-036 · 2026-10-01 · accepted — Anime section: ani-cli runs inside the app (Linux only)
- **What:** a new section downloads anime episodes (and, later, whole seasons) through ani-cli, kept in a local SQLite library (`node:sqlite`, available in the Node 24.21 that Electron 44 ships; verified) and played inside the app (`<video>` served by a custom protocol). It exists on Linux only. This entry covers the whole section: the ani-cli base layer, the library, the queue, the player and the screens.
- **ani-cli as an external program, like yt-dlp:** the script is pinned to a master commit (version 5.1.4, the latest tagged release is older and different) and checked by sha256. It has no structured output, so searching and listing are done by letting it ask for a choice: `ANI_CLI_MENU` points at `pullwave-menu`, which reports every choice on stderr (`PULLWAVE_MENU<TAB>prompt<TAB>line`, stdout is captured by ani-cli) and fails so ani-cli stops. A choice is later made with `-S <position>`, an episode with `-e <n>`, the audio with `ANI_CLI_MODE`. Positions only mean something inside the same search, so the library keeps the title and the query.
- **Nothing from the system:** `busybox` (static, 1.35.0, x86_64) runs the script (`busybox sh ani-cli`) and answers to `sed`, `grep`, `cut`... through symlinks made at run time in `userData/anime/tools` (symlinks are not reliable in electron-builder extraResources); a static `curl` (stunnel/static-curl 8.22.0) does the requests; yt-dlp and ffmpeg are the ones the app already uses (the chosen ones, linked too). The PATH holds the links and the bundled folder only. busybox.net publishes no checksum, so the hash of the file is pinned in `fetch-binaries.mjs`. Only x86_64, like the rest of the bundle.
- **Stand-ins (`resources/ani-scripts`, tracked in git):** `pullwave-menu` (above), `pullwave-noplayer` (ani-cli refuses to start on Linux without mpv or vlc, even to download; `ANI_CLI_PLAYER` points at a program that exits 0) and `tput` (cosmetic, busybox has none).
- **Input is untrusted:** ani-cli reads any word that looks like a flag (`-d`, `-U`, `-D` wipes its history) and pastes the query into an address unencoded, so `aniArgsBuilder` keeps letters, digits and `' . : ! , -`, strips leading dashes and validates position, episode (`^\d+(\.\d+)?$`) and quality.
- **Edge cases found with the real ani-cli:** with a single result ani-cli picks it without asking (only the episode list shows) and with a single episode (a film) nothing is asked at all and it ends with code 0; the service reports a lone result as position 1 titled with the query and confirms episode `1` with a second run (only trusted if ani-cli accepts it). Progress lines are not kept in the text saved for an error (they would only make it grow).
- **Verified here:** real search (several results, none, one), episode list, and one real episode downloaded with `-q worst` (about 104 MB, `<title> Episode N.mp4` plus a `.vtt`) with the same tools and an isolated PATH. Not verified: dub, seasons, other providers' failures, packaged build.
- **Legal/availability:** the source ani-cli scrapes can change or block at any time (`BLOCKED` is mapped); the same disclaimer of D-020 applies.

- **Library (`animeDb.ts`, `node:sqlite`):** `userData/anime/anime.db`, versioned migrations (`PRAGMA user_version`, each in a transaction). Tables `anime` (unique by title and audio, so the dubbed version is a different anime; the search and the position are refreshed on every download because the position only holds for one search) and `episode` (unique per anime and number; status, file, size, last error, position, duration, watched). Episodes are numbered with text and sorted as numbers. The queue is in memory, so at start whatever was `queued` or `downloading` becomes `error` ("closed before the download finished") and can be retried from the library.
- **Queue (`animeDownloadQueue.ts`):** one job per episode (a whole season is just all its episodes), `maxConcurrent` at a time, in order; episodes already downloaded or already waiting are skipped; each anime has its own folder inside the anime folder (`animeDownloadDir`, or `Downloads/Pullwave Anime`); progress is reported only when it moves by half a percent; a file that is not there when ani-cli says it is done is an error; cancel, retry (also for episodes left over from an earlier run) and clear finished.
- **Player (`mediaProtocol.ts`):** a `pullwave-media://episode/<id>` (and `subtitle/<id>`, the `.vtt` ani-cli saves beside the video) scheme served by the main process with byte ranges (200/206/416/404), so the HTML5 `<video>` can seek. Addresses carry an id, never a path, and only downloaded episodes of the library resolve. The CSP gets `media-src 'self' pullwave-media:`; `fetch()` from the page stays blocked by `connect-src`, which is fine. The player saves the position every 5 seconds, on pause and on close, resumes from it (unless almost nothing or almost everything was watched), counts 90% as watched and offers the next downloaded episode. Chromium may not play every codec; the player then says so.
- **Where it shows:** the ANIME tab and the ANIME settings panel only exist when the main process says the section is supported (Linux). Elsewhere the IPC channels still answer, saying it is unsupported, and the protocol and database are never created.
- **Test hook:** `PULLWAVE_ANI_CLI` replaces the ani-cli script (like `PULLWAVE_APPLICATION_DIRS` does for the browsers); the end-to-end tests point it at `test/e2e/fixtures/fake-ani-cli.sh`, which logs its calls in the history folder.
- **Verified with the real thing:** the app was driven end to end (search, open, download episode 1 at the lowest quality, library, play: 640x360, 1444 s, seek by range, subtitles shown). Not verified: dub, seasons of a real anime, other sources failing, the packaged build.
